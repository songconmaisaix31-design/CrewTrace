## 多主体信任架构

实验中存在五个角色，分别运行在独立进程中，只通过公开目录交换数据：

- 签发主体 A：独立签发密钥、履约凭证、信誉事件与密钥轮换历史。
- 签发主体 B：独立签发密钥、履约凭证与信誉事件，与 A 不共享密钥或数据库。
- 未授权主体 C：自行声明身份并使用自己的密钥签发凭证，但不出现在任何已签名信任配置中。
- 独立审批者：使用与签发密钥无关的私钥为受控代码样本签发执行授权，私钥不导出。
- 验证主体：持有独立预置的信任根公钥，加载签名信任配置，按自身策略决定接受哪些签发者。

信誉事件键为 `issuerId|subjectNamespace:subjectValue|taskType|eventId`，分桶键同时包含 `issuerId`、`taskType`、主体、服务、环境、部署与规则版本。A 与 B 使用相同事件标识时仍进入不同分桶；同一主体重复提交同一凭证被判为重复；不同签发来源不合并为全局信用分。

## 可验证信任配置

`ct-trust-config-v1` 包含版本、签发时间、有效期、信任根、签发者名单、撤销列表、配置摘要与签名。摘要为 `keccak256(UTF8("ct-trust-config-v1:" + canonicalJson(payload)))`。

`loadTrustConfig` 依次校验结构、重算摘要、根公钥匹配、恢复签名者、生效与过期时间、版本下限、可选固定摘要、名单元数据与时效、撤销列表元数据、时效与未来撤销时间。失败时返回 `TRUST_CONFIG_DIGEST_MISMATCH`、`TRUST_CONFIG_SIGNATURE_MISMATCH`、`TRUST_CONFIG_ROOT_MISMATCH`、`TRUST_CONFIG_EXPIRED`、`TRUST_CONFIG_ROLLBACK`、`TRUST_CONFIG_REVOCATION_INTEGRITY` 等错误码。

实验验证了同时信任 A 与 B、只信任 A、拒绝 C、密钥轮换后核验历史凭证、识别已撤销凭证、识别已撤销密钥，以及拒绝被篡改、过期、回滚与根公钥不匹配的配置。配置签名只证明配置由预置信任根签发，不代表名单内签发者的信誉获得独立认证。

## 多主体凭证交换与核验结果

验证方同时信任 A 与 B 时，A 与 B 的 CSV 凭证、A 的历史凭证、A 与 B 的代码凭证全部通过复算并准入；信誉分桶为 `issuer-a|csv-data-review`、`issuer-a|code-artifact-test`、`issuer-b|csv-data-review`、`issuer-b|code-artifact-test`。A 的历史凭证由轮换前密钥签发，在密钥退役但未撤销时仍被判定为活动密钥。

只信任 A 时，B 的 CSV 与代码凭证均以 `ISSUER_UNKNOWN` 被拒绝。提交 C 的凭证时，即使签名与结构有效，也因不在签名配置中而被拒绝。撤销 A 的当前凭证后，只有该凭证被拒绝，A 的历史凭证与 B 的凭证不受影响。撤销 A 的轮换前密钥后，只有使用该密钥的历史凭证被拒绝。

## 代码执行授权

代码验证器不再仅凭凭证内容执行代码。`verifyAttestation` 在执行前要求凭证签名有效、签发者已知、密钥活动、撤销状态清晰、规则版本已识别，并校验由独立审批密钥签名的 `ct-code-execution-grant-v1`。授权绑定交付摘要、测试集合摘要、执行器标识、签发与过期时间。未授权、审批地址不受信、授权过期、摘要不匹配或自签授权都会阻止执行。直接调用验证器并传入未授权状态时快速返回 `UNRESOLVED`，不运行挂起的测试样本。

内置验证器列表、目录返回值与解析结果在运行时冻结。Node `vm` 仅用于经过审查的受控合成样本，不宣传为第三方任意代码安全沙箱。

## 本地链上承诺实验

在隔离 Hardhat（chain ID 31337）上复用现有 `CollaborationLedger`，不新增合约。两个签发主体分别签发凭证并写入链上承诺，链上只保存 `kind`、`recordId`、`version`、`contentHash` 与 `uri`。

独立读者通过 `scanCommitments` 与 `makeChainReader` 回读记录，确认两份承诺的摘要与凭证摘要一致、记录者为受控记录账户、签发地址与记录地址不同。验证方同时核验签发者名单与记录者白名单后，两份凭证均为 `PRESENT_MATCH` 与 `VERIFIED`。

未授权签发者的凭证可以存在链上承诺，但因签发者不在名单中被拒绝。验证方配置错误的记录账户时得到 `CHAIN_RECORDER_UNAUTHORIZED` 与 `PRESENT_MISMATCH`。非记录账户尝试写入时交易回滚。撤销凭证后，链上历史承诺仍可读，但验证结果为 `REVOKED` 与 `REJECTED`。

## 签名凭证与链上承诺的对照

修改已上链凭证的交付摘要并使用原签发密钥重签后，签名本身有效，但链上核验返回 `PRESENT_MISMATCH` 与 `CHAIN_COMMITMENT_MISMATCH`，结论为 `REJECTED`。这说明签名证明凭证由签发者签发，链上承诺证明某个摘要曾被记录，两者不能互相替代：签名有效不代表内容与历史承诺一致，链上承诺存在也不代表凭证可信。

## 剩余中心化信任边界

- 信任根私钥由单一受控操作者持有，没有透明日志、多签、门限签名或硬件密钥。
- 签名配置由同一操作者生成，签发者名单的加入与移除没有独立监督或争议流程。
- 撤销列表分发依赖验证方主动获取，没有公开可见的撤销广播。
- 记录账户是单一受控账户，链上承诺不证明记录者中立。
- 本地 Hardhat 结果不代表公共链跨机器可用性。
- 代码执行使用 Node `vm`，不是完整安全沙箱。
- 信誉分桶只在单次聚合与调用方传入的历史事件范围内去重，没有跨进程全局约束。
- 所有签发者、审批者与验证者均为受控实验角色，不是真实独立组织。

## Monad Testnet 必要性

本地实验已经验证签发者、记录者、凭证摘要与链上承诺的关系，也能验证撤销、未授权记录者与内容差异。公共测试网能额外验证公共 RPC 可达性、跨机器独立回读与浏览器可见性，但不改变信任模型。当前没有外部开发者要求公共链回读证据，因此本轮不部署。提案见 `monad-testnet-proposal.md`，状态为 `NOT_DEPLOYED`，等待单独批准。
